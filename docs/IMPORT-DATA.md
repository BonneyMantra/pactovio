# Customer product imports

The import keeps source records staged before any catalogue write. A user can inspect and analyze grounded fields while data is incomplete. Optional technical/category/features gaps do not block approval. Included records require a name, usable description, selling price with currency/unit, and internal purchase/manufacturing unit cost with its own currency/unit. Unsupported currencies or inexact money require explicit completion; neither blank nor unknown becomes zero. Explicit zero needs a corresponding per-row confirmation. Manufacturer SKU is optional; missing SKUs receive an identified internal catalogue reference, not a claimed manufacturer code.

`POST /api/integrations/workflows/imports/:id/normalize` accepts `{revision}` only after authenticated user action. It invokes the existing Nebius fast structured-output client, including the hard product daily cap and kill switch. It suggests exact source column mappings and source-header currency hints; it cannot supply row prices or missing currencies. Users review suggestions and explicitly confirm constant currencies. Ambiguous Amount or conflicts need user decisions. On cap/provider failure the job stays staged and manual mapping/completion works. Successful interpretations are saved per job revision; a replay returns that checkpoint.

Source-linked preview rows retain `source_record`, `field_sources`, a valid partial `candidate`, and `optional_gaps`. `product` stays null when required values fail validation; `unresolved` prevents frozen approval. Per-row `resolutions` preserve actual manual decisions. Re-preview and explicit approval apply only the frozen hash and revision. All target/provenance writes share the existing D1 transaction guard. Later manual edits change product revision; reimport surfaces a conflict instead of overwriting them.

Internal cost is stored separately in `product_costs`, scoped to workspace and product. Authenticated catalogue reads join it. Quote generation and model catalogue readers never join this table; outgoing quote/proposal structures contain selling prices only. Legacy product records remain intact without fabricated cost backfill and show missing completion fields when edited.

For Google Sheets, optional `header_row:true` consumes the first selected row as native headers. The explicitly selected `identity_column` supplies stable nonempty unique IDs; no special schema/header names are required. When used, IDs are **workbook-wide**: imports from other tabs of the same workbook/account with the same ID refer to the same product, even when the ID column label differs. Select IDs that are stable and unique across that catalogue. Headerless legacy ranges retain previous positional behavior. Staging never writes to the source.

The RAX fixture's complete/required/optional/messy tabs intentionally reuse source IDs. Import each scenario separately to test updates/conflicts without inflating catalogue count. Its commercial values are individually synthetic; public descriptions and technical fields retain source provenance. Creating that private Sheet through the connected Google Drive does not connect a Pactovio customer account. The exact Pactovio-specific Composio project currently has no Google Sheets auth config, and production lacks the callback verifier flag; full live-source E2E remains unverified until that integration is configured and exercised.
